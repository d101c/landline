Landline 0.1 — notes for the reviewer

Architecture, in brief
- extension.js wires three things: a client of a local Unix socket (lib/engineClient.js), a state model with no GLib or Shell import (lib/model.js and lib/model/, unit-tested outside the Shell), and the views (lib/indicator.js, lib/cards.js, lib/setup.js, lib/notifications.js).
- The model receives the engine's JSON events and the user's actions, and view() returns what the top bar, the card and the setup dialog must show. It sets no timer: extension.js keeps a single timeout for its next deadline.
- prefs.js is a plain Adw window bound to the GSettings schema. It imports only lib/setupHelper.js, which imports lib/subprocess.js and lib/names.js (Gio and GLib, no Shell library).
- Nothing is created before enable(). disable() removes every source, ends the subprocesses still running (see below for the one exception), closes the socket, disconnects the settings and destroys the indicator, every setup dialog not yet destroyed (including one fading out) and the notification sources.
- No synchronous file or process call in the Shell process: file attributes are read with query_info_async, drawings with load_contents_async, subprocesses are awaited.
- No telemetry, no bundled binary or script: the zip contains only GJS, CSS, SVG, the schema and the licence. Two kinds of network request: the engine download described below (preferences window, on a click), and the app icons described below (Shell process, asynchronous, can be turned off).

Why an external engine
Linking an iPhone means acting as a Bluetooth accessory: pairing with a dual (Classic + LE) bond, ANCS over GATT for notifications, MAP and PBAP through obexd for messages and contacts, hands-free for calls, and keeping those links alive across sleep and range losses. That is a long-running C++ service (derived from Tether by Zack Bartel, MIT) and cannot reasonably live in the Shell process. It runs as a systemd user service (landline-engine.service). The extension is a front end to it, in the same way other extensions are front ends to syncthing or ddcutil. Without the engine the extension shows "Landline needs its engine" with an "Install the Engine…" button that opens the preferences, and does nothing else. Instructions and the manual way: https://github.com/d101c/landline#install

Installing the engine (prefs.js, lib/enginePage.js, lib/engineInstaller.js; never in the Shell process)
- Pinned in the code, nowhere else (lib/engineRelease.js): the version, the URL of the release archive on github.com, its SHA-256, and the SHA-256 of the two files of it that the system step runs as root. No remote manifest is read.
- On a click on Install or Update: download with libsoup 3 into ~/.cache/landline, SHA-256 checked (a wrong file is deleted), unpacked with libgnome-autoar into ~/.local/lib/landline/.staging, contents checked, then switched in (engine -> engine.old, kept for "Use Previous Engine"; engine.new -> engine). It writes ~/.config/systemd/user/landline-engine.service and obex.service.d/landline.conf, then calls systemd over D-Bus (Reload, EnableUnitFiles, ResetFailedUnit, RestartUnit) and waits for the engine's socket to answer. No process is started for any of this.
- "Uninstall the Engine…": StopUnit, DisableUnitFiles, the files above removed, Reload.
- Closing the preferences window cancels what runs and aborts and releases the Soup.Session (closeSession() in lib/engineInstaller.js, called by EngineInstaller.destroy()).
- The one pkexec of this page that does not target the root-owned helper (point 6 below).

Why the system step runs a shell script through pkexec (the password dialog says "run /bin/sh")
Right after the first install there is no root-owned file yet: the helper that will live in /usr/local/libexec/landline is still in the user's home folder, which the user (or any process of theirs) can change. Running that file with pkexec would run a user-writable file as root, and a polkit action of our own cannot exist before something has been installed as root. So the one first elevation goes through /bin/sh, which is root's, with a script that is a constant string of this version of the extension (bootstrapScript() in lib/engineInstall.js). The SHA-256 of the two files it may run are written into that string, taken from lib/engineRelease.js, where they are pinned together with the SHA-256 of the release archive; they are never arguments, settings or downloaded values. The script copies the two files into a new directory of root (mktemp -d under /run, mode 0700), checks the sums of the copies, and runs only those copies; anything else exits 66 before running anything. The generic "/bin/sh" wording of the dialog is the price of not running a home-folder file as root. After that first run the helper and its polkit action are root's, and every later elevation (points 4 and 5) targets that fixed root-owned path, with the extension's own message in the dialog. The commands shown for doing it by hand check the same two pinned sums with sha256sum -c before sudo.

Every subprocess the extension starts
1. systemctl --user start landline-engine.service — extension.js, _startEngine(). Once each time the socket stops answering, before saying the engine is not running.
2. systemctl --user restart landline-engine.service — extension.js, _restartEngine(). Only on a click on "Fix It".
3. <setup helper> status — lib/setupHelper.js, SetupHelper.status(). Read-only, no privilege: prints one JSON line saying whether the Bluetooth settings an iPhone needs are in place. Run at enable(), after an "apply", and every two seconds only while the setup dialog is showing the commands to run by hand. The helper is /usr/local/libexec/landline/landline-setup, or the copy a local install leaves in ~/.local/lib/landline/. It is installed with the engine; it is not in the zip. If neither exists nothing is run.
4. pkexec /usr/local/libexec/landline/landline-setup apply — lib/setupHelper.js, runAsRoot(), from the setup dialog on a click on "Continue". See below.
5. pkexec /usr/local/libexec/landline/landline-setup revert — the same function, from prefs.js, on a click on "Undo" in the settings window, or on "Uninstall and Undo Bluetooth Changes…" in Phone Settings › Engine. Only when that file passes the same check as for 4 (owned by root, not writable by group or others, executable). Declared in the description, like 4.
6. pkexec /bin/sh -c '<script>' landline-bootstrap <path of landline-setup> <path of landline-le-params> — lib/enginePage.js, askPassword(), on a click on "Continue…" at the "Bluetooth settings" step, right after an engine install, when the root-owned helper is not there yet. The script is a constant of this version (bootstrapScript() in lib/engineInstall.js); the two expected SHA-256 are part of its text, not arguments. It copies both files into a new root-owned directory (mktemp -d /run/landline-setup.XXXXXX, 0700), checks the SHA-256 of the copies, and only then runs the copy ("bash <copy> apply"), which installs itself and the helper into /usr/local/libexec/landline (root:root 0755); the directory is removed by a trap. Wrong sum: exit 66, nothing runs. A file the user can write is never executed as root: what runs is the root-owned copy whose content was checked after copying.
1 to 6 all go through one function, run() in lib/subprocess.js: Gio.Subprocess with an argument vector (no string built from user input; the only shell is 6, given a constant script and the two paths as separate arguments), awaited with wait_async / communicate_utf8_async, never a synchronous wait.

What disable() does to a subprocess still running
run() is given a Gio.Cancellable that disable() cancels (for 5, the settings window cancels it when it closes). Cancelling ends the wait and calls Gio.Subprocess.force_exit(), which sends SIGKILL:
- 1 and 2: the systemctl client is ended. The start or restart job it had already handed to systemd is systemd's and is not undone.
- 3: the helper's read-only status command is ended.
- 4 and 5: while the password window is up, pkexec (setuid, real uid still the user's) can be signalled: it is ended, and the helper is never started, so nothing is changed. Once the password has been accepted the helper runs as root and a signal from the user cannot reach it (force_exit() then does nothing): it is left to finish (it writes a few configuration files, reloads systemd and udev and may restart bluetooth.service) rather than stopped half-way. The extension no longer waits for it and ignores its result.
After disable() no new subprocess is started: run() starts nothing once its cancellable is cancelled.

Not subprocesses, but worth knowing
- Gio.AppInfo.launch_default_for_uri() — lib/notifications.js, on a click on the "Reply in app" action of a WhatsApp, Telegram or Signal notification. The URI (lib/replyLinks.js) is https://web.whatsapp.com/send?phone=…, tg://resolve?phone=… or sgnl://signal.me/#p/…, with the sender's number.
- libnm (gi://NM, imported on demand in lib/hotspot.js) — activates or deactivates the Bluetooth connection profile NetworkManager already holds for the paired iPhone, on a click on "Use iPhone's Internet Connection". Nothing is created or deleted.
- Gio.Settings on org.gnome.desktop.notifications (lib/quiet.js) — read only, to follow Do Not Disturb.

Where privilege is raised, and why never on a user-writable path
Two system settings may be missing: BlueZ's experimental mode (needed before BlueZ 5.88) and L2CAP ERTM (disabled on some systems). Both need root. The extension never writes them itself and never elevates anything from its own directory or from the home directory:
- pkexec is only ever given the fixed path /usr/local/libexec/landline/landline-setup (a constant in lib/names.js; no environment variable, no setting, no argument changes it), and only after rootHelper() in lib/setupHelper.js has checked that the file is owned by uid 0, is not writable by group or others, and is executable.
- That file is put there by the engine's installer (the helper copies itself to the root-owned directory the first time the user runs it with sudo, together with a polkit action for the password dialog's message), never by the extension.
- When the root-owned copy is absent, no password is asked from the Shell at all: the dialog shows the command to run in a terminal, with a "Copy Commands" button, and continues by itself once the settings are in place.
- On a system where both settings are already right (the common case with a recent BlueZ), this step does not exist.

What shexli reports (0.2.1)
- EGO-A-005, clipboard: true and intended. extension.js _copyCommands() writes the commands above to the clipboard on a click on "Copy Commands"; in the preferences, "Copy Commands" of Phone Settings › Engine writes the manual install steps (GTK clipboard). Nothing is ever read. Declared in the description.
- EGO-M-004, shell-version: shexli does not know GNOME 51 yet. The metadata lists 51 only: it is the one release the extension was run on, and its menus use the open()/close() parameters of 51 ({animate: false}), which GNOME 50 does not have.

App icons (lib/appIcons.js, in the Shell process)
- What is sent: each iPhone notification names its app by its bundle identifier. To show that app's real icon, the extension asks Apple's public lookup, GET https://itunes.apple.com/lookup?bundleId=<identifier>&country=<region of the locale, or us>, then downloads the icon from the artworkUrl it returns, rewritten to 128x128 PNG and accepted only over HTTPS on *.mzstatic.com. Nothing else of the notification (sender, text) is ever sent. No key, no account.
- Once per app: one request in flight per app at most; the PNG (checked: image/png, PNG signature, 512 KiB at most) is kept in ~/.cache/landline/app-icons/<identifier>.png and read from there afterwards. An app the App Store does not know leaves a one-byte <identifier>.none marker and is not asked again for 24 hours; a network or server error is remembered in memory for 24 hours too.
- Non-blocking: libsoup 3 send_and_read_async, query_info_async, make_directory_async, replace_contents_bytes_async, all with a Gio.Cancellable. disable() calls AppIcons.destroy(): the cancellable is cancelled, the Soup.Session is aborted and dropped.
- Setting "show-app-icons" (Phone Settings › Notifications of other apps › Show app icons), on by default, with a sentence that says the app identifier is sent to Apple's App Store. Turned off: nothing is sent and the cached icons are not shown.
- Fallbacks: the icon of the same app installed on the computer (Shell.AppSystem.lookup_app() on a fixed table of desktop ids: signal-desktop, org.telegram.desktop, com.microsoft.Teams…), then the initials. No brand logo is shipped in the zip.
- Display: the PNG is the background-image of an St.Bin with a CSS border-radius (rounded like an iPhone icon); no image processing.

Other things you may ask about
- session-modes is not set: the extension is disabled on the lock screen.
- The model is one class assembled from one module per subject (lib/model/*.js, each a function that extends the class it is given), so that each subject can be read on its own.
- The four drawings of iPhone screens in illustrations/ are my own SVGs, with no Apple artwork or logo. "iPhone" is used in the texts only to name the phone.
